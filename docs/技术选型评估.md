# 技术选型评估

> 对应中期答辩评委第四类质疑：「BGE-M3 有点老 / 用得相对少 / 方案不太一致」「ChromaDB 为什么这么用」
> 「瓶颈可能在输入层的切分，也可能在存储层」
> 评估日期：2026-07-31｜数据口径：`eval_results_v7full`（55 本 / 4432 题）

---

## 零、先说一个必须撤回的旧论证

此前对「是否更换嵌入模型」的答复是：

> Hit@5 已 100%，天花板到顶，换任何更强模型分数也超不过 100%。

**这个论证现已作废，两处都站不住：**

1. `Hit@5` 是**指标误称**。代码里 `hit()` 是在**模型答案文本**中查关键词，不是检索命中率，
   应叫「答案关键词覆盖率」（会话六 §9.4 已认定）。
2. 100% 出自旧的 61 题小样本。扩到 4432 题后，可答 93.9%、模糊 47.4%，**远未到顶**。

拿这个理由去答辩，一问就穿。下面用本轮实测重新论证。

---

## 一、检索是不是瓶颈？——先定位，再谈换不换

评委提示「瓶颈可能在输入层的切分，也可能在存储层」。本轮 v6–v7 排查恰好给出了直接证据。

### 证据一：模糊题失败的是生成，不是检索

v6 故障期，模糊题严格命中掉到 17.9%，逐题看：

```
Q: cornea blindness condition
A: [p.955]                    ← 页码引对了，正文一个字没写
```

- 空壳答案（剥掉引用标记后正文为 0）占 fuzzy_desc 的 **59.3%**
- 其中 **12/28 道 `ok_loose=True`** —— 页码命中，即**检索取到了正确的块**
- 根因定位为 ollama 服务端 0.31.1→0.32.3 改变了 `think=False` 下的生成行为，
  补一句提示词即恢复（V3），检索侧一行未改

### 证据二：严格与宽松口径的差值来自措辞

v7full：模糊题严格 47.4% / 宽松 54.5%。逐题归因（`compare_runs.py`）显示，
v3→v7 的 97 道「改坏」中 **63 道（65%）是两边都作答、仅措辞不同**：

```
Chemistry_2e   An amorphous solid is...     →  An amorphous substance is...
Microbiology   Disease control involves...  →  To control disease, ...
```

答案正确，只是关键词没匹配上。**这部分差距靠换嵌入模型解决不了。**

### 证据三：切分层确实动过，且影响巨大

评委猜测的「输入层切分」是对的——本项目所有重大回归都出在这里：
`HEADING_RE` 窄化导致模糊题 −22pp、`LIST_ITEM_RE` 导致 −4.2pp，两次都在回归验证中被拦下。
为此建立了分块指纹机制（`chunking_fingerprint()`），凡影响切分的改动一律留痕。

### 结论

**当前瓶颈在生成端与评测判据，不在检索召回。** 因此更换嵌入模型或向量库
在现有语料上**测不出收益**——但这次是有证据的结论，不是「已经 100% 了」这种空话。

## 二、嵌入模型：bge-m3 → 暂不更换

| 维度 | bge-m3（现用） | Qwen3-Embedding-0.6B（候选） |
|---|---|---|
| 维度 | 1024 | 1024（**同维，可平替不需改库结构**） |
| 显存量级 | 同量级 | 同量级 |
| Ollama 支持 | ✅ | ✅ |
| 多语言 | ✅ | ✅ |
| 发布时间 | 2024 | 2025 |

**评委说「有点老」属实**，bge-m3 是 2024 年的模型。但：

1. 上一节已证明检索不是当前瓶颈，换了在本语料上测不出差异
2. 同为 1024 维，**迁移成本极低**——改 `EMBED_MODEL` 常量 + 重建库即可，
   不需要改分块、打包、引用溯源任何一层

**迁移触发条件（写死，不留模糊）**：语料扩至 100+ 本后，若可答严格命中率跌破 90%，
且失败题的 `ok_loose` 比例显著上升（说明检索取错块而非生成写不出），即启动 A/B。

**未换的诚实表述**：不是「不需要换」，是「当前语料下换了测不出差异，且迁移路径已备好」。

## 三、向量库：ChromaDB → 保留；FAISS → 明确不适用；Qdrant → 生产升级目标

评委问「ChromaDB 为什么这么用」，并建议参考 FAISS。逐一回应：

### FAISS 对本项目是降级，不是升级

| 能力 | 本项目是否依赖 | FAISS | ChromaDB |
|---|---|---|---|
| 向量检索 | ✅ | ✅ 更快 | ✅ |
| **元数据存储**（页码/来源/类型） | ✅ **引用溯源的地基** | ❌ 无 | ✅ |
| **持久化** | ✅ 离线交付必需 | ❌ 需自建 | ✅ |
| 按元数据过滤（`where`） | ✅ 分型检索消融用到 | ❌ 需自建 | ✅ |

本系统的核心卖点是**带页码的引用溯源 + 引用校验**（`_labeled_context` 注入真页标签、
`verify_citations` 事后交叉核对）。这条链**完全建立在元数据之上**。

换 FAISS 意味着要自己实现元数据存储层、持久化层、过滤层——**把 ChromaDB 重写一遍**，
换来的只是检索速度提升，而检索在本项目的耗时占比可忽略（4432 题 token 中位 394，
瓶颈在 LLM 生成）。

**这是架构不匹配，不是懒得换。**

### Qdrant 才是正确的升级方向

若未来需要生产级部署（多集合、并发、水平扩展、混合检索），Qdrant 是对的目标——
它同时具备 ChromaDB 的元数据能力和更强的工程特性。当前单机离线场景用不上。

### 「根据显存权衡」——评委原话的正面回应

评委问 ChromaDB 时特别加了一句「根据显存」。实测数据：

| 组件 | 显存/内存占用 | 说明 |
|---|---|---|
| `qwen3:8b` Q4_K_M | 约 5.2GB 显存 | 生成的绝对大头 |
| `qwen3-vl:8b` | 约 6.1GB 显存 | 仅建库期加载，问答期不占 |
| `bge-m3` | 约 1.2GB 显存 | 1024 维 |
| **ChromaDB** | **不占显存** | 纯 CPU/磁盘，HNSW 索引常驻内存约 4.2MB/万块 |

实测 A&P 单本 9402 块，索引目录 4.2MB、库总计 84MB。**向量库根本不是显存瓶颈**，
显存全被 LLM 占着。换 FAISS（GPU 版）反而会去和 LLM 抢显存。

因此「根据显存权衡」的结论是：**在 16GB 显存的单机场景下，向量库应当避开显存**，
ChromaDB 的纯 CPU 设计恰好正确；把显存留给 8B 模型全量驻留，才是这台机器上的最优分配。

### ChromaDB 的已知代价

诚实列出：单 collection 设计、`build` 会删库重建、无内置多租户。
本项目为单机离线单用户场景，这些不构成约束；扩展到多用户即需迁移 Qdrant。

## 四、生成模型与 VL 模型

| 组件 | 选型 | 理由 |
|---|---|---|
| LLM | `qwen3:8b` Q4_K_M（5.2GB） | 8B 量级在 RTX 5090 Laptop 上可全程 GPU；Q4_K_M 是质量/显存的平衡点；支持 `think` 开关（本项目关键依赖） |
| VL | `qwen3-vl:8b` | 与 LLM 同族，部署一致；实测单页读图 42s（均值） |

**已知风险（v6 事件教训）**：`think=False` 的行为依赖 ollama 服务端版本，
0.31.1→0.32.3 曾导致模糊题 −30pp。**跨版本升级必须重跑回归。**
现已将 ollama 服务端版本、ollama-py 版本、模型量化等级纳入运行指纹（`env_fingerprint()`）。

## 六、准确性口径：按评委定义应主报双口径

评委对准确性的定义是原话「**不是一字不差而是理解即可**」。这条直接影响指标呈现。

v3→v7 的 97 道「改坏」经机制归因，**63 道（65%）是两边都作答、仅措辞不同**：

```
Chemistry_2e   An amorphous solid is...     →  An amorphous substance is...
Microbiology   Disease control involves...  →  To control disease, ...
```

严格口径按关键词精确匹配判负，但**按评委的定义这些都算对**。因此报告应：

- **主报严格口径**（可答 93.9% / 模糊 47.4%）作为保守下界
- **并列宽松口径**（可答 94.4% / 模糊 54.5%）并注明其含义
- 明确说明严格口径带 ±1–2pp 判定噪声，来源是关键词匹配对措辞敏感
